# 《팔대신병록》 메타 프롬프팅 프로토콜 v1

상태: `active-protocol`
적용 범위: 설계·감사·리서치·코드·이미지 등 AI에게 작업을 위임할 때 사용하는 프롬프트 생성과 검증
상위:
- `book_writing.md`
- `CLAUDE.md`
- 최신 사용자 결정

---

## 1. 목적

좋은 프롬프트는 지시문을 길게 쓰는 것이 아니라 다음을 분명하게 만드는 작업이다.

1. AI가 알아야 할 사실
2. AI가 물어봐야 할 미확정 사항
3. 반드시 지켜야 할 제약
4. 성공을 판정할 수 있는 조건
5. 실행환경에 맞는 출력 형식
6. 실패하거나 막혔을 때 멈추고 보고할 기준

이 프로토콜은 다음 3단계를 기본으로 한다.

> **컨텍스트 덤핑 → 프롬프트 깎아내기 → 결과물 점검**

# 2. 1단계 — 컨텍스트 덤핑

## 2.1 원본 덤프와 실행 프롬프트를 분리한다

컨텍스트 덤핑은 필요한 정보를 전부 모으는 단계이지, 그대로 최종 프롬프트에 붙이는 단계가 아니다.

두 파일 또는 두 구역으로 분리한다.

### A. 원본 컨텍스트 팩

포함:

- 사용자 목표와 최신 결정
- 현재 상태와 승인 상태
- 정본·후보·폐기안
- 관련 파일과 인용 가능한 근거
- 용어·금지선
- 이전 실패와 계획 이탈
- 실행환경과 도구 제약
- 원하는 결과물 예시

### B. 실행용 브리프

원본 팩에서 현재 작업에 필요한 것만 추려 다음 순서로 압축한다.

1. 역할
2. 목표
3. 입력
4. 반드시 유지할 사실
5. 하지 않을 것
6. 성공조건
7. 작업 순서
8. 출력 형식
9. 중지요건
10. 결과 점검표

원칙:

- 원본 컨텍스트 팩은 길어도 된다.
- 실행용 브리프는 중복을 없애고 판단에 필요한 최소 정보만 남긴다.
- 같은 사실이 여러 문서에 있으면 최신 상위 문서를 기준으로 하나만 적는다.
- 충돌하는 정보는 숨기지 말고 `충돌 항목`으로 분리한다.

## 2.2 AI에게 질문을 유도한다

프롬프트를 만들기 전에 AI에게 다음을 시킨다.

> 지금까지 제공된 대화와 자료를 바탕으로 작업 프롬프트를 만들 예정이다. 정확한 프롬프트 작성에 필요한 정보가 부족하다면, 이미 답한 내용을 반복하지 말고 결과를 크게 바꾸는 질문만 최대 3개 물어라.

질문 규칙:

- 한 번에 최대 1~3개
- 이미 답한 질문 금지
- 취향의 이름보다 결과를 묻기
- 답에 따라 산출물이 실제로 달라지는 질문만 하기
- 사소한 누락은 합리적 기본값 또는 표시된 플레이스홀더로 처리
- 사용자가 `진행`, `계속`이라고 했다고 고영향 선택을 승인한 것으로 보지 않기

좋은 질문:

- 무료분 5화 끝에서 독자가 기다려야 할 것은 `첫 호송 출발`, `라이벌 정체`, `분점 폐쇄 명령`, `첫 신병 흔적` 중 무엇인가?
- 서유휘가 결말에서 가장 크게 잃는 것은 직업 신용인가, 가족 가업인가?

나쁜 질문:

- 어떤 분위기를 원하나요?
- 더 자세히 알려주세요.

## 2.3 컨텍스트 우선순위

충돌 시 우선순위:

1. 최신 사용자 결정
2. `book_writing.md`
3. `CLAUDE.md`
4. 해당 Gate의 승인 결정
5. 정본 마스터
6. 후보·감사·장부
7. 과거 참고안

과거 문서가 최신 결정을 덮어쓰지 못한다.

# 3. 2단계 — 프롬프트 깎아내기

## 3.1 덜어내기 기준

초안 프롬프트를 만든 뒤 각 문장을 다음으로 분류한다.

- `MUST`: 틀리면 결과를 사용할 수 없음
- `SHOULD`: 품질을 크게 높임
- `MAY`: 있으면 좋지만 없어도 됨
- `REMOVE`: 반복·배경 설명·현재 작업과 무관

최종 실행 프롬프트에는 `MUST`와 핵심 `SHOULD`만 본문에 둔다. `MAY`는 참고 부록으로 보낸다.

삭제 대상:

- 같은 목표의 반복 표현
- 이미 입력 파일에 있는 긴 요약
- 실행자가 판단하지 않아도 되는 역사
- 결과 형식에 영향을 주지 않는 수사적 설명
- 서로 충돌하는 모호한 형용사
- `최고로`, `완벽하게`, `멋지게`처럼 검증 불가능한 말

## 3.2 목표·제약·성공조건을 분리한다

### 목표

무엇을 만들어야 하는가.

예:

> 한국 무협 웹소설 《팔대신병록》의 무료분 1~5화 기능 설계 네 안을 만든다.

### 제약

어떻게 하면 안 되는가.

예:

- 회귀·빙의·시스템을 추가하지 않는다.
- 원고 문장이나 대사를 쓰지 않는다.
- 기존 50장안을 자동 복원하지 않는다.
- 팔대신병 현물을 모두 모으지 않는다.

### 성공조건

완료 여부를 관찰 가능하게 만든다.

예:

- 1화 첫 화면 안에 `표사·인계·조선소 위기·서유휘 판단`이 보인다.
- 3화 안에 첫 승패 또는 비가역 손실이 있다.
- 5화 끝에는 장기 호송을 시작할 이유와 반복 적대선이 분명하다.
- 각 화에 목표·압력·선택·다음 질문 중 최소 3개가 있다.
- 네 시안은 서로 다른 재미 엔진을 사용한다.

## 3.3 중지요건을 명시한다

에이전트가 억지로 계속하지 않도록 멈출 조건을 적는다.

중지요건 예:

- 사용자 승인이 필요한 C2~C3 결정에 도달함
- 입력 문서의 상태가 서로 충돌함
- 필수 자료가 없고 합리적 기본값으로 대체하면 결과가 크게 달라짐
- 새 설정이 정본과 충돌함
- 요구한 파일을 읽을 수 없음
- 도구 제한으로 검증을 수행할 수 없음
- P0 맹점 발견

중지할 때 출력:

1. 어디서 멈췄는가
2. 왜 멈췄는가
3. 이미 완성한 것
4. 필요한 사용자 결정 또는 자료
5. 선택 가능한 기본안과 영향

# 4. 실행환경에 맞게 프롬프트 변환

같은 목표라도 실행환경마다 프롬프트 구조를 바꾼다.

## 4.1 Goal Prompt / 일반 작업 에이전트

필수 항목:

- 역할
- 단일 목표
- 입력 자료
- 성공조건
- 작업 순서
- 중지요건
- 출력 형식

템플릿:

```text
역할: [전문 역할]
목표: [단일 산출물]
입력: [파일·대화·데이터]
반드시 유지: [정본·용어·사용자 결정]
제약: [하지 않을 것]
성공조건: [관찰 가능한 체크리스트]
작업 순서: [분석→시안→권고→감사]
중지요건: [승인 필요·자료 충돌·도구 실패]
출력: [파일명·표·섹션]
```

## 4.2 Ultracode / 코딩 에이전트

추가 필수 항목:

- 저장소·브랜치·대상 경로
- 수정 가능한 파일과 금지 파일
- 기존 인터페이스·스키마·스타일 유지
- 테스트·린트·타입체크 명령
- 보안·성능·호환성 제약
- 마이그레이션 허용 여부
- 같은 파일 쓰기 순서
- 실패 시 롤백 또는 변경 로그

성공조건 예:

- 모든 버튼·폼이 실제 동작한다.
- 모바일 첫 화면 안에 핵심 가치와 CTA가 보인다.
- 기존 테스트를 깨지 않고 신규 테스트를 추가한다.
- 오류·빈 상태·로딩 상태를 처리한다.
- 실행 명령과 검증 결과를 보고한다.

중지요건 예:

- API 계약이 불명확함
- 비밀키·외부 권한이 필요함
- 데이터 손실 가능성이 있음
- 기존 스키마 변경이 필요한데 승인되지 않음

## 4.3 이미지 생성

필수 항목:

- 목적과 사용처
- 피사체
- 구도
- 전경·중경·배경
- 동작과 표정
- 시대·복식·소품
- 스타일과 매체
- 색감
- 조명
- 카메라 높이·각도·렌즈감
- 화면비
- 반드시 포함할 것
- 제외할 것

검증 항목:

- 핵심 피사체가 한눈에 보이는가
- 손·무기·문양·글자가 깨지지 않았는가
- 시대와 복식이 설정에 맞는가
- 배경이 주인공보다 튀지 않는가
- 이미지가 실제 사용처의 비율과 여백을 만족하는가

## 4.4 리서치 에이전트

필수 항목:

- 조사 질문
- 조사 범위와 제외 범위
- 기준 날짜
- 우선 출처
- 허용·금지 출처
- 최신성 기준
- 최소 교차검증 수
- 사실·해석·추론 구분
- 인용 형식
- 반대 자료 처리
- 찾지 못했을 때 보고 방식

출처 우선순위 예:

1. 1차 사료·공식 문서·원문
2. 학술 연구·대학·박물관
3. 전문 출판사·공신력 높은 매체
4. 보조 블로그·커뮤니티는 단서로만 사용

검증 방식:

- 핵심 주장마다 독립 출처 2개 이상
- 날짜·수치·명칭은 1차 출처 우선
- 출처가 충돌하면 양쪽을 제시
- 추론은 추론이라고 표시
- 못 찾은 정보는 만들어내지 않기

## 4.5 소설 설계 에이전트

필수 항목:

- 플랫폼·장르·독자층
- 작품의 한 문장 약속
- 현재 Gate와 승인 상태
- 정본 유지 항목
- 이번에 설계할 단위: 대서사·막·소구간·화
- 재미 성공조건
- 인물·설정·플롯 금지선
- 사용자 승인이 필요한 결정

한국 웹소설 성공조건 예:

- 1~5화 안에 주인공·직업·위기·장기 목표가 각인된다.
- 10~15화 안에 첫 소구간 보상이 있다.
- 매 화에 목표·압력·선택·다음 질문 중 최소 3개가 있다.
- 설정 설명은 행동·관계·손실 안에서만 전면화한다.
- 막마다 통쾌한 승리와 주인공 책임의 손실이 각각 있다.

# 5. 3단계 — 결과물 점검

## 5.1 1차 자기점검

실행 에이전트는 결과 뒤 다음 표를 채운다.

| 성공조건 | 충족 여부 | 근거 위치 | 미충족 조치 |
|---|---|---|---|
| 조건 | pass/fail/partial | 파일·섹션·화 | 수정안 |

자기점검은 `잘했다`는 평가가 아니라 산출물의 위치와 증거를 제시해야 한다.

## 5.2 2차 독립 점검

중요 작업은 작성 프롬프트와 별도의 비평 프롬프트로 검토한다.

비평 에이전트 역할:

- 작성자의 의도를 변호하지 않는다.
- 성공조건과 금지선만 기준으로 본다.
- P0/P1/P2로 문제를 분류한다.
- 누락·중복·충돌·과잉·실행 불가능성을 찾는다.
- 최소 한 개의 반대 가설을 검토한다.

비평 프롬프트 예:

```text
아래 산출물을 작성자의 설명이 아니라 성공조건만 기준으로 감사하라.
각 문제를 P0/P1/P2로 분류하고, 근거 위치와 최소 수정안을 제시하라.
`통과`를 기본값으로 두지 말고, 결과가 실제 환경에서 실패했다고 가정한 반대 가설을 최소 3개 검토하라.
```

## 5.3 결과물 품질 질문

- 목표와 다른 것을 잘 만들지는 않았는가
- 결과를 실제로 사용할 수 있는가
- 성공조건을 관찰 가능하게 충족했는가
- 입력에 없는 사실을 발명하지 않았는가
- 중요한 예외와 실패 상태를 처리했는가
- 계획과 달라진 지점을 기록했는가
- 사용자가 결정해야 할 것을 AI가 몰래 확정하지 않았는가
- 결과가 너무 길어 핵심 행동이 묻히지 않았는가

# 6. 프롬프트 생성용 메타 프롬프트

다른 AI에게 최종 작업 프롬프트를 만들게 할 때 사용한다.

```text
지금까지 제공한 대화·문서·결정을 바탕으로 [작업명]을 수행할 AI용 실행 프롬프트를 작성하라.

먼저 다음을 하라.
1. 최신 목표·정본·후보·금지선을 분리하라.
2. 결과를 크게 바꾸는 정보가 부족하면, 이미 답한 내용을 반복하지 말고 질문을 최대 3개만 하라.
3. 질문이 필요 없으면 바로 프롬프트를 작성하라.

프롬프트에는 반드시 포함하라.
- 역할
- 단일 목표
- 입력 자료
- 유지할 사실
- 제약조건
- 관찰 가능한 성공조건
- 작업 순서
- 중지요건
- 출력 형식
- 결과 점검표

초안 뒤에는 프롬프트를 깎아내라.
- 중복을 제거하라.
- MUST/SHOULD/MAY를 구분하라.
- 실행에 필요 없는 배경은 부록으로 보내라.
- 모호한 형용사는 측정 가능한 조건으로 바꿔라.

마지막으로 실행환경이 [Goal Prompt / Ultracode / 이미지 생성 / 리서치 / 소설 설계] 중 무엇인지에 맞게 변환하라.
```

# 7. 금지사항

- 컨텍스트를 많이 넣는 것 자체를 품질로 착각하지 않는다.
- 내부 추론 전체를 요구하지 않는다. 대신 근거·결정·검증표를 요구한다.
- 상충하는 지시를 한 프롬프트 안에 방치하지 않는다.
- 성공조건 없이 `잘`, `멋지게`, `전문적으로`만 지시하지 않는다.
- 중지요건 없이 에이전트가 임의로 정본을 확장하게 하지 않는다.
- 결과 점검을 같은 문장으로 `스스로 검토해`라고만 끝내지 않는다.
- 실행환경에 맞지 않는 출력 형식을 강요하지 않는다.
- 사용자 승인이 필요한 결정을 자동 확정하지 않는다.
